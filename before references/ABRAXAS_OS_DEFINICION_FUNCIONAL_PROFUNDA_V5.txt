ABRAXAS OS — DEFINICIÓN FUNCIONAL PROFUNDA V5
Documento de arquitectura funcional, lógica de fondo y relación entre herramientas
Fecha: 2026-08-28

======================================================================
0. OBJETIVO DE ESTE DOCUMENTO
======================================================================

Este documento no intenta resumir ABRAXAS OS en una frase corta. Su objetivo
es explicar cómo piensa el sistema, qué problema resuelve, por qué existen sus
módulos, qué información es responsabilidad de cada uno, cómo se conectan y
qué debe ocurrir desde que aparece una oportunidad de contenido hasta que esa
pieza se publica, produce métricas y modifica el aprendizaje futuro.

La definición funcional debe servir para:

- explicar ABRAXAS OS a una persona nueva;
- orientar a un diseñador o desarrollador;
- evitar duplicar responsabilidades entre módulos;
- permitir que Arquitecto explique el sistema;
- distinguir inteligencia, interfaz, producción y evidencia;
- preservar la filosofía original de ABRAXAS mientras se moderniza;
- servir como autoridad conceptual antes de implementar nuevas funciones.

Este documento describe principalmente la arquitectura objetivo aprobada.
Cuando se menciona implementación histórica o estado real, debe validarse
contra el repo y los tests antes de afirmar que está funcionando hoy.

======================================================================
1. QUÉ ES ABRAXAS OS
======================================================================

ABRAXAS OS es un sistema operativo para crear, producir, organizar, gerenciar,
publicar y aprender de contenidos de manera trazable.

Su diferencia principal frente a una aplicación de marketing convencional es
que no trata cada fase como una herramienta aislada.

No existe una app para ideas desconectada de otra para copy, otra para video,
otra para calendario y otra para métricas sin una memoria común.

ABRAXAS intenta mantener una identidad continua:

CLIENTE
   ↓
OPORTUNIDAD
   ↓
PLAN
   ↓
LIENZO
   ↓
FUENTES / GRABACIÓN
   ↓
RESOLUCIÓN
   ↓
PRODUCCIÓN
   ↓
QA
   ↓
PUBLICACIÓN
   ↓
MÉTRICAS
   ↓
APRENDIZAJE

La pieza conserva el mismo content_id durante todo ese recorrido.

El sistema busca que una decisión tomada temprano pueda ser entendida más
tarde y que un resultado posterior pueda explicar de dónde vino.

Por eso ABRAXAS OS no se define por una pantalla.
Se define por una red de objetos, criterios, contratos, estados y eventos.

======================================================================
2. LA TESIS CENTRAL: CONVERTIR CRITERIO EN INFRAESTRUCTURA
======================================================================

Una gran parte del trabajo creativo tradicional depende de conocimiento
implícito:

“este hook funciona para este cliente”;
“esta toma necesita un push-in”;
“este carrusel no debe cerrar así”;
“esa promesa no está respaldada por la fuente”;
“este copy no coincide con lo que realmente se grabó”;
“esta estructura ya se usó demasiado este mes”;
“este editor está bloqueado esperando aprobación”.

ABRAXAS busca convertir ese conocimiento implícito en objetos reutilizables:

CLIENT CORE
FORMAT
STRUCTURE
PATTERN
PROMPT COMPONENT
COPY PROFILE
VISUAL CRITERIA
MOTION FAMILY
SOURCE CLAIM
TASK
DEPENDENCY
EVENT
ARTIFACT
PUBLICATION TARGET
METRIC SNAPSHOT
LEARNING SIGNAL

La frase “convertir criterio en infraestructura” significa que una decisión
editorial o productiva importante debe poder almacenarse, consultarse,
versionarse, reutilizarse, compararse y auditarse.

======================================================================
4. YOD — EL CEREBRO DE INTELIGENCIA Y MEMORIA
======================================================================

YOD existe porque la inteligencia de contenidos no debe quedar repartida en
cientos de HTMLs, prompts o archivos específicos de clientes.

YOD representa la memoria estructurada de ABRAXAS.

YOD responde preguntas como:

- ¿qué sabemos de este cliente?
- ¿qué temas y pilares trabaja?
- ¿qué estructuras existen?
- ¿qué estructura encaja con este objetivo?
- ¿qué formatos ya usamos demasiado?
- ¿qué tipo de hook está repetido?
- ¿qué promesas puede hacer esta marca?
- ¿qué fuentes respaldan una afirmación?
- ¿qué contenido hace falta crear?
- ¿qué contenido funcionó antes?
- ¿qué patrón conviene repetir o evitar?
- ¿qué prompt debe compilarse para esta tarea?
- ¿qué visual cumple una función real?
- ¿qué copy necesita este canal?
- ¿qué motion es semánticamente adecuado?

YOD no debe “tener creatividad” como una caja negra.

Debe almacenar y combinar criterios explícitos.

----------------------------------------------------------------------
4.1 Client Intelligence
----------------------------------------------------------------------

Client Intelligence representa la memoria estable y versionada de cada marca.

Debe distinguir:

IDENTIDAD
- propósito;
- posicionamiento;
- tono;
- personalidad;
- vocabulario;
- restricciones.

NEGOCIO
- oferta;
- audiencia;
- objetivos;
- productos;
- mecanismos;
- diferenciadores.

CONTENIDO
- pilares;
- formatos;
- canales;
- cadencia;
- niveles de profundidad;
- tipos de CTA.

SOURCE TRUTH
- hechos aprobados;
- fuentes;
- claims permitidos;
- claims prohibidos;
- incógnitas.

LEARNING
- hipótesis aprendidas;
- estructuras que mejor rinden;
- temas saturados;
- hooks exitosos;
- tiempos de producción;
- observaciones.

La regla importante es:
LEARNING no debe sobrescribir SOURCE TRUTH.

Una inferencia estadística del sistema no se convierte automáticamente en
verdad de marca.

======================================================================
5. LIENZO — EL OBJETO VIVO DE CADA CONTENIDO
======================================================================

Lienzo es probablemente el objeto más importante de ABRAXAS OS.

No es una tarjeta de Trello.
No es un HTML.
No es un formulario.
No es un render.

Es la identidad persistente de una pieza.

Debe poder responder:

¿qué intentábamos hacer?
¿qué planeamos?
¿qué material llegó?
¿qué encontró Shim?
¿qué resolvimos?
¿qué copy estaba aprobado?
¿qué versión de portada generó este JPG?
¿qué motion produjo este render?
¿quién aprobó?
¿dónde se publicó?
¿qué métricas obtuvo?
¿qué aprendimos?

----------------------------------------------------------------------
5.1 Capas del Lienzo
----------------------------------------------------------------------

CORE:
identidad estable.

STRATEGY:
objetivo, audiencia, pilar, tesis.

PLANNED:
lo que se esperaba producir.

OBSERVED:
lo que realmente está presente en la fuente.

RESOLVED:
decisión editorial confirmada.

PRODUCTION:
edit, captions, motions, audio, visuales.

DISTRIBUTION:
variantes/assets finales.

PUBLICATION:
targets y snapshots.

LEARNING:
métricas y observaciones.

HISTORY:
versiones, eventos y decisiones.

Nunca mezclar:
PLANNED
con OBSERVED
con RESOLVED.

======================================================================
6. SHIM — DE MATERIAL REAL A DECISIÓN EDITORIAL
======================================================================

Shim existe para evitar que el sistema crea que lo planeado es exactamente lo
que ocurrió en una grabación.

Shim toma material real:

video
audio
transcript
documentos
entrevista
podcast
source assets

y responde:

¿qué se dijo?
¿qué existe?
¿quién lo dijo?
¿en qué timestamp?
¿qué estructura puede construirse?
¿qué falta?
¿qué claim está respaldado?
¿qué candidato merece revisión?

Pipeline:

SOURCE
→ INGEST
→ TRANSCRIBE / PARSE
→ SEGMENT
→ DETECT CANDIDATES
→ MATCH STRUCTURES
→ FIND GAPS
→ HUMAN REVIEW
→ RESOLVE
→ UPDATE LIENZO

Shim no debe inventar un beat que no está grabado.

Si falta:
FOUND / MISSING.

YOD puede formular una pregunta.
Arquitecto puede guiar una nueva toma.
La nueva toma vuelve a Shim.

7. VAV — BRAZO DE PRODUCCIÓN AUDIOVISUAL
======================================================================

VAV recibe intención estructurada.

No debería tener que adivinar:
qué queremos decir;
qué hook usar;
qué claim es cierto;
qué estructura conviene.

Su trabajo es materializar.

Áreas:

CUTS
CAPTIONS
MOTIONS
SIMPLE MOTION
VISUAL LAYERS
AUDIO
VFX
SFX
RENDER
QA
EXPORT

Cada acción relevante debe devolver estado al Lienzo.

Ejemplo:

CAPTIONS_COMPLETED
version: 4
artifact: CAPTION_PLAN_004
rendered: true

No basta con guardar:
final_v7_REAL_final.mp4

Debe existir Artifact Registry.

12. ROUNDTRIP — IA EXTERNA SIN INTEGRACIÓN
======================================================================

AI_RESULT.txt

Dos capas:

HUMAN RESPONSE
+
MACHINE RESULT JSON

PARSE
→ VALIDATE
→ QA
→ DIFF
→ HUMAN ACCEPT
→ LIENZO

======================================================================
19. APPROVALS, PERMISSIONS Y RESPONSABILIDAD
======================================================================

Para operar equipos profesionalmente se necesitan dos capas adicionales.

RBAC:
qué puede hacer cada persona.

APPROVAL:
quién tiene que aceptar una versión.

Ejemplo:

Editor termina Edit Lock.
Producer approves.
Motion starts.
QA waits.
Manager can override.

Sin esto, He sería un Trello bonito, no una herramienta gerencial.

20. AUTOMATION RULE ENGINE
======================================================================

La gestión puede automatizarse con reglas explícitas.

WHEN Edit Lock DONE
THEN create Captions Task
AND notify Caption Editor.

WHEN deadline <24h
AND status != DONE
THEN notify Manager.

WHEN Shim GAP detected
THEN create Recording Follow-up.

Automation no debe ser IA arbitraria.

TRIGGER
CONDITIONS
ACTIONS

28. QUÉ NO DEBE VOLVERSE ABRAXAS
======================================================================

No debe convertirse en:

- un monolito donde cada módulo conoce todo;
- un generador de texto sin contratos;
- un sistema que inventa evidencia;
- un gestor de archivos sin provenance;
- un Trello desconectado de producción;
- un editor que ignora estrategia;
- una IA que cambia contenido sin review;
- una colección de HTMLs independientes;
- un sistema donde el mismo dato se copia en cinco sitios;
- una plataforma que obliga a abandonar herramientas externas;
- una base donde todas las versiones antiguas se destruyen.

======================================================================
29. DEFINICIÓN FINAL
======================================================================

ABRAXAS OS es una infraestructura creativa y operativa versionada donde el
conocimiento de marca y contenido vive en YOD; cada pieza conserva su identidad
en un Lienzo; Shim compara intención con evidencia real; VAV materializa la
producción audiovisual; He coordina personas, tareas, calendarios, deadlines,
publicación y métricas; Arquitecto acompaña al usuario con contexto del sistema
y criterio de YOD; AI Runtime permite usar lógica, IA externa, APIs, Ollama,
MCP o modelos locales sin cambiar los contratos; Publishing distribuye
snapshots controlados; Metrics devuelve desempeño real; y el aprendizaje
resultante vuelve a YOD sin borrar la historia ni convertir inferencias en
verdad de marca.

La arquitectura busca que cada decisión sea:
trazable,
editable,
versionada,
explicable,
reutilizable,
auditable,
y conectada con el resultado que produjo.
